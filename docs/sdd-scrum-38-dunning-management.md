# SDD: SCRUM-38 — Dunning Management для неудачных рекуррентных списаний

**Статус:** реализовано по тексту задачи  
**Поток:** А — рекуррент и эквайринг  
**Трекер:** Кузьменко Степан. В бэклоге: Чубаров Егор.

Списание периода: `docs/sdd-scrum-36-recurring-payments.md`. Обход due-строк: `docs/sdd-scrum-37-billing-scheduler.md`.

---

## 1. Контекст

`charge_subscription` при отказе ЮKassa откатывал транзакцию и не менял подписку. Планировщик брал только `active`, поэтому повторного списания по регламенту dunning не было. Покупатель не узнавал, почему автодоставка не прошла.

## 2. Цели (DoD)

1. При ошибке списания подписка переходит в `past_due`, `next_billing_at` сдвигается на интервал ретрая.
2. Покупателю уходит сервисное письмо с причиной и ссылкой на обновление карты.
3. На третьей неудаче подписка становится `cancelled` и выпадает из биллинга.
4. Сценарии покрыты pytest.

## 3. Не-цели

- Экран обновления карты. В письме только ссылка из `CARD_UPDATE_URL`.
- Новые колонки и миграции. Хватает `status`, `dunning_attempts`, `next_billing_at`.
- Dunning, если склад пуст или код карты не читается: запроса в кассу не было, дата не двигается.
- Dunning, если ЮKassa вернула `succeeded` или `paid=true`, но сумма или валюта не сошлись. Деньги могли уйти, повтор создал бы второе списание.
- Dunning на HTTP 4xx и на неразобранный JSON: это не отказ банка. Дата не двигается, тот же Idempotence-Key можно повторить.
- Платёж в статусе `pending`. Это не финальный отказ.
- Возврат уже прошедшего платежа.

## 4. Решение

| Тема | Выбор |
|------|--------|
| Где | `plan_dunning` в `app/services/dunning.py`. Оркестрация остаётся в `charge_subscription`: та же транзакция, что держит `FOR UPDATE` подписки и карты |
| Кого списываем | `active` и `past_due` с непустым токеном. `cancelled` — ошибка до HTTP |
| Что считаем отказом | `status=canceled` и `paid=false`, сеть (`AcquirerUnavailableError`), HTTP 5xx |
| Причина в письме | `cancellation_details.reason` только если код из `[a-z0-9_]{1,64}`. В письмо идёт русский текст известного кода, иначе «Банк отклонил платёж». Сырой код и тело ответа в письмо не попадают. Сеть и 5xx — «Временная ошибка банка…» |
| Счётчик | `dunning_attempts += 1` на каждый такой отказ |
| Пауза | После 1-й неудачи — 1 сутки, после 2-й — 3 суток, статус `past_due`. Считается от `now`, не от старой даты: опоздавший проход не ставит ретрай в прошлое |
| Третья неудача | `cancelled`, `dunning_attempts=3`, `next_billing_at` не сдвигается. Письмо об аннулировании автодоставки, без ссылки «обновите карту» и без обещания следующей попытки |
| Лестница «1, 3 и 5» | Константа `DUNNING_RETRY_DAYS`. Пятые сутки не пишутся в календарь: подписка уже закрыта и исключена из выборки. Иначе планировщик списал бы её четвёртый раз |
| Успех после `past_due` | Снова `active`, `dunning_attempts=0`, `next_billing_at = прежняя дата периода + 30 суток`. Якорь — дата попытки, как в SCRUM-36, а не `now` |
| Транзакция | Отказ: карта не меняется, заказа нет, один `commit` со статусом подписки. Успех: как раньше, плюс `status=active`. Чужой незакоммиченной работы в сессии быть не должно |
| Письмо | После `commit`, отдельной задачей. Ошибка SMTP не откатывает dunning. Сервис не импортирует FastAPI |
| Ссылка | `Settings.card_update_url` / `CARD_UPDATE_URL`. В письмо проходит только `http://` или `https://` без пробелов и перевода строки, иначе дефолт `http://localhost:8000/account/payment-method` |
| Планировщик | `lock_next_due_for_billing` берёт `active` и `past_due` с `next_billing_at <= now`, `FOR UPDATE SKIP LOCKED`. `cancelled` не берёт. `list_active_due_for_billing` по-прежнему только `active` |
| Идемпотентность | Ключ периода прежний: дата `next_billing_at`. Сдвиг на сутки даёт новый ключ, повтор не получает закэшированный `canceled` |
| Логи | Id подписки, статус, число попыток, id платежа и код причины. Email, URL и `payment_method_id` в лог не пишутся |

Потерянный ответ `succeeded` при сетевой ошибке и следующий ретрай с новым ключом могут списать второй раз. То же окно, что у обрыва после `succeeded` до `commit` в SCRUM-36. Отдельные inflight-поля не заводим.

## 5. Интеграция

| Место | Действие |
|-------|----------|
| `app/services/dunning.py` | План паузы, текст причины, нормализация ссылки |
| `app/services/recurring_payments.py` | Запись dunning, допуск `past_due`, очередь письма |
| `app/services/payments.py` | `cancellation_reason`, `status_code` у ошибки HTTP |
| `app/services/email.py` | Сборка и отправка сервисного письма |
| `templates/email/subscription_dunning.html` | Общий шаблон предупреждения и аннулирования |
| `app/repositories/subscriptions.py` | В блокирующую выборку добавлен `past_due` |
| `app/config.py`, `.env.example` | `CARD_UPDATE_URL` |
| Роуты, схема БД | Без изменений |

## 6. Тесты

База `awe_test`, ЮKassa замокана.

- Лестница: 1 сутки, затем 3; третья неудача отменяет и не сдвигает дату. Наивная дата отклоняется.
- Нехватка средств, блокировка карты, временная недоступность банка, неизвестный код — разные тексты; код с разметкой отбрасывается.
- Письмо-предупреждение содержит причину и ссылку. HTML экранирует причину. Письмо об аннулировании говорит, что автодоставка закрыта и новых списаний не будет.
- Первая и вторая неудачи: `past_due`, карта `available`, заказа нет, ключ следующей попытки другой.
- Третья неудача: `cancelled`, планировщик её больше не списывает.
- HTTP 500 двигает dunning. HTTP 400, пустой склад, битый код и `succeeded` с чужой суммой — не двигают.
- Успешный ретрай из `past_due` возвращает `active` и обнуляет счётчик.
- Ошибка постановки письма не маскирует уже записанный отказ.
